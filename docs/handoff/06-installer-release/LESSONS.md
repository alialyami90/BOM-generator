# LESSONS — role 6 (append-only)

- **Self-test reads a build-time module manifest, not the frozen app.** Decision: `packaging/bomgen.spec` writes `bomgen_modules.txt`; `--self-test` imports every listed module and checks `bomgen/app/ui/index.html`. Why: walking the frozen app only sees modules PyInstaller kept, so a dropped module passes (proven with a fake module). Rejected: runtime `pkgutil` walk.
- **Native non-zero exit codes leak out of a pwsh step.** After an expected non-zero exit (`--help` before the CLI existed) reset `$global:LASTEXITCODE = 0` and end with `exit 0`. Learned from run 5d23a23.
- **PowerShell reads `$name:` as a scope prefix.** `"... $LASTEXITCODE: $x"` fails to parse; write `${LASTEXITCODE}:`. A unit test now rejects the pattern (#57). Learned because #55 merged before its Windows job finished; A1 now waits for the job on release.yml changes.
- **The frozen CLI skips `cli.main()`.** `launcher.cli_main` calls the typer app directly, so any setup in `main()` (UTF-8 console) must also run in `cli_main` (#70). Test with cp1252 stdout/stderr.
- **`build` prints the workbook path first, then the check report.** The smoke step takes only line 1 as the path, then asserts `.checks.json` exists and the report says "0 failed".
- **A release made by hand blocks `gh release create`.** Ali published an empty v0.1.0 in the UI before the tag run, so the publish job failed. Fix: delete the empty release (keep the tag) and "Re-run failed jobs", then the workflow guard (`gh release view` then `upload --clobber`) so it cannot recur (#86).
- **Tag name case matters.** The workflow triggers on `v*`; Ali's first v0.1.1 tag was `V0.1.1`, so no run started. Ask Ali for the exact commands and verify with `list_tags`.
- **Tag pushes from the sandbox return HTTP 403.** Don't look for another route; hand Ali the two commands.
- **First-start default library: launcher hook, not an installer [Run] step.** Why: the Windows smoke test can start the installed app on a fresh `BOMGEN_LIBRARY_HOME` and diff the store snapshot after a reinstall; an installer step would write to the runner's real store. Rule: import only when `LibraryStore.list()` is empty, never force, and never block the window on a failure. A double-clicked `.bomlib` skips it.
- **Branch restarts.** The remote branch holds old squashed history and force pushes are denied: `git checkout -B claude/project-thread-y4aekh origin/main` then `git merge -s ours origin/claude/project-thread-y4aekh` and a normal push.
- **Test environment drift.** After main changes dependencies run `pip install -e ".[dev,app]"` again; a stale or non-editable install once made tests run old code, and a new dev dependency (pycel) broke collection.
- **Cancelled runs look like failures.** A push cancels the previous run; its `ci-status` shows failure on the old sha. Check the newest run before fixing anything.
- **Tag the commit the changelog covers.** Ali tagged v0.1.1 on the latest main, past the 0.1.1 changelog; Ali's rule: no release with a missing changelog. Before following a tag run, compare the tag sha with the commit A1 named; if they differ, cancel before the publish job and ask A1.
- **A retag that "is done" may not be on GitHub.** Ali's local retag of v0.1.1 never reached GitHub because the old tag still existed there. Always check with `list_tags` or `git ls-remote` before following a run. From a phone the route is: delete the tag in the UI, then publish a release with a new tag on the chosen commit (the workflow attaches the installer).
- **Release from main, not from tags (#153).** Agents can't push tags, so tag-driven releases stalled on Ali. Rule: a merged version bump with its changelog section is the release; the workflow refuses without the changelog section (Ali's rule). Rejected: a separate tagging workflow (a tag made with GITHUB_TOKEN would not trigger it).
- **Handoff drift (B6, 2026-10-28).** NEXT's Q38 review assumed main still packed 1.0.0; main already packed and checked psa-devices 1.1.0, so only the pack path changed. Read the main file before reviewing against NEXT. Also `pip install -e ".[dev,app]"` fails on Linux (pywebview's proxy_tools wheel); use `.[dev]` for the gate here.
- **A fast Windows job is not a skipped one.** With a pip cache hit the "Build Windows installer" job runs in about 90 s. Check the job's steps all ran (`get_workflow_job`) and the log ends with "Installed, verified and uninstalled".
