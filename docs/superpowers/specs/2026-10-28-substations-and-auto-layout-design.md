## 1. What Ali asked for

Written back from the project thread so it can be corrected. "Said" is Ali's
words; "assumed" is this design's reading, to be confirmed.

**Projects and substations (said).** A project holds several substations.
Each substation has one system: its own panels, BOM, calculation sheets and
workbook. The project holds the project info, the document list and any data
shared by its substations. A substation can be created from an existing one as
a template. The home page lists all projects. Engineers share work by exporting
and importing one `.bomproj` file; backups are saved copies.

**Field IEDs (said).** IEDs never appear in the BOM, not even as a count. Their
number is an input asked for per substation; it only sizes the L1 switches.

**Switch sizing (said).** L1 switches connect the field IEDs and are sized from
the IED count. L2 switches carry all other substation equipment (GPS,
controllers, gateways, …) plus the L1 switches, which connect in a star, so L2
is sized from that equipment and from the number of L1 switches. A checkbox
chooses ring or star topology. Port sizing keeps 20 % spare, and every spare
(ports and everything else) is user-defined so it can change later.

**Panels (said).** Panels are 42U but only 32U may be used, keeping 10U for
expansion. Devices are not stacked one U after the other: one blank plate sits
between neighbours. Overflow goes to a new panel. For every redundant pair the
A device sits in panel 1 and the B device in panel 2, so losing one panel's
power loses only one side.

**Manual control (said).** In the UI, drag a device (single or pair) from one
panel to another, or delete it.

**Assumed.**
- The IED count is one number per substation, not per bay or voltage level.
- Blank plates are real parts and go in the BOM (one commodity catalogue entry).
- The L2 switches themselves are an A/B pair; L1 switches are A/B pairs.
- Devices that have no side (today's cabinet 003: GPS clock, RTAC, Axion I/O)
  fill their own "common" panel(s) after the A and B panels.
- The WS console stays a hand-written panel; the layout engine does not touch
  `kind: console` panels.
- Today's spec example (cabinets 001/002/003 + WS) must still come out of the
  new inputs unchanged, so all golden values stay valid.

## 2. Structure: workspace, project, substation

```
<workspace>                       a folder the app remembers (Documents\BOM Generator)
  <project-id>/
    project.yaml                  project info, document register, shared data
    substations/
      <substation-id>/
        substation.yaml           today's project.yaml, renamed (see 3.2)
        panels/*.yaml             generated by the layout engine (+ hand-written console)
        out/                      workbooks and check reports (git-ignored style)
    Backups/
      <project-id>-<timestamp>.bomproj
```

- **`project.yaml`** (new): `project: {id, name, client, logo}`,
  `library: {name, version}` (the installed library every substation uses),
  `documents:` the register (section 3.1), `defaults:` design constants and
  spares inherited by substations, `substations: [substations/<id>/substation.yaml]`.
- **`substation.yaml`**: everything today's `project.yaml` holds (name, doc
  numbers, calc documents, output, constants, loose material) plus the new
  `equipment`, `network` and `layout` sections (3.2). Constants and spares
  override the project defaults key by key.
- **"Create substation from template"** copies a substation folder, asks for
  the new id, substation name, cabinet numbers and tag prefixes, and clears
  `layout.overrides`. It is a file copy plus a rename pass; no new model.
- **`.bomproj`** is a zip of one project folder (without `out/`) plus
  `manifest.json` (format version, project id, library name and version,
  app version, SHA-256 per file). Export writes it; import unpacks it into the
  workspace and warns before overwriting an existing project id. Backup is
  export into `Backups/`. The format, checksums and path checks reuse A5's
  `.bomlib` code (`library_store.package`), and the manifest records which
  library version the project was built with (plan Q21), so import tells the
  engineer which `.bomlib` to install if theirs differs.

## 3. Inputs

### 3.1 Document register (project level)

```yaml
documents:
  - { key: psa1-bom,          doc_no: VD-EL0009-861GISPSA-001, rev: "02", issue_date: 2026-10-28 }
  - { key: power_consumption, doc_no: VD-EL0009-861GISPSA-002, rev: "00", issue_date: 2026-10-28 }
```

Each substation's panels and calculation sheets name the register key they
print in their header (`document: psa1-bom`), so one transmittal list drives
every header. Ali is asked (Q24) whether the register is per project or per
substation; this design puts it on the project with keys prefixed by
substation id, which covers both.

### 3.2 `substation.yaml` additions

```yaml
equipment:                       # what the substation has, before panels exist
  - { part_id: RST2228-L2,  role: l2_switch,  redundant: true }     # one per side
  - { part_id: RST2228-L1-24MM, role: l1_switch, redundant: true }  # count is computed
  - { part_id: SEL-2730M-EXT, role: ext_switch, redundant: true }
  - { part_id: FW-EXT, role: firewall, redundant: true, l2_ports: 1 }
  - { part_id: FOPP-96SM, role: fopp, redundant: true }
  - { part_id: SEL-2488, role: other, side: none, l2_ports: 1 }      # GPS: common panel
  - { part_id: SEL-3555-RTAC, role: other, side: none, l2_ports: 2 }
  - { part_id: SEL-2240, role: other, side: none, l2_ports: 0 }

network:
  ied_count: 40                  # field IEDs; never a BOM row
  topology: star                 # star | ring
  ring_max_switches: 6           # ring only: L1 switches per ring, user-defined
  l1_uplinks_per_switch: 2       # ports each L1 uses towards its L2 (star)
  l3_uplinks_per_l2: 2           # SM uplinks to the control room (today's uplinks_l3)

spares:                          # every spare is user-defined; defaults = today's values
  port_fraction: 0.20            # keep 20 % of each switch's ports free
  sfp_per_l1: 3                  # today's "=24+3"
  dc_branches_per_feed: 3
  ac_branches: 1
  rack_u_reserved: 10            # 42U panel, 32U usable

layout:
  panel_capacity_u: 32           # = enclosure_u - spares.rack_u_reserved; shown, not edited
  blank_plate_part: BLANK-1U     # catalogue part placed between neighbours
  overrides:                     # written by the UI's drag-and-drop; hand-editable
    - { device: PSA1-L1-ESW-A13, panel: 3 }       # move one device
    - { pair: EXT-FW, panel: [3, 4] }             # move an A/B pair
  removed: [PSA1-DHPCC-GW-1]                      # deleted from the BOM
```

Library additions (A2's schema, data from A3): `height_u` on every rack-mounted
device (0 for DIN-rail parts, which do not count against the 32U), and on
switches the port roles the sizer needs: `ports[].usable_for: ied | uplink | any`.
The catalogue gains `blank_plate: {part_id}` and `enclosure_u: 42`.

Today's `panels/*.yaml` keep their schema unchanged; the layout engine writes
them (`generated: true` header) and the rest of the pipeline consumes them as
before. The hand-written console panel is listed in `substation.yaml`
`manual_panels: [panels/ws.yaml]`.

## 4. Rules (the spec addendum)

**R1 L1 switch count.** Per side,
`usable = floor((ports_total − l1_uplinks_per_switch) × (1 − spares.port_fraction))`,
`n_l1 = ceil(ied_count / usable)`. Example: RST2228 has 28 ports; 28 − 2 = 26;
26 × 0.8 = 20.8 → 20; 40 IEDs → 2 L1 switches per side (matches Ali's example).

**R2 L2 port demand.** Per side, `demand = Σ equipment.l2_ports (devices on that
side or common) + l1_links`, where `l1_links = n_l1 × l1_uplinks_per_switch` in a
star, and `2 × ceil(n_l1 / ring_max_switches)` in a ring (two ports close each
ring). `usable_l2 = floor((ports_total − l3_uplinks_per_l2) × (1 − port_fraction))`,
`n_l2 = ceil(demand / usable_l2)`. Spec example: 6 L1 × 1 link + GPS 1 = 7 ≤ 20
→ one L2 per side, as today.

**R3 Port plans and SFPs follow the sizing.** The generated port plan for each
L2 lists `uplinks_l3`, the L1 links as 1G MM downlinks and the equipment ports
by speed/media from the library; each L1 gets `uplinks: ports_used + spares.sfp_per_l1`.
So "Derivation rules → Network accessories" is unchanged; only its inputs are
now computed.

**R4 IEDs never appear.** No BOM row, description, count or note mentions the
IEDs; `ied_count` is printed only on the check report.

**R5 Panel fill.** Devices are placed in BOM group order (A → H, as the spec
lists them) into panels of `panel_capacity_u`. A device costs `height_u`, and
every neighbour pair costs one blank plate (1U), so a panel with k rack devices
uses `Σ height_u + (k − 1)`. DIN-rail parts (MCBs, terminals, relays) cost 0U.
When the next device does not fit, a new panel of the same stream starts.

**R6 Streams and symmetry.** Three streams: A (every `redundant: true` device's
A unit, odd panels 1, 3, …), B (its B unit, even panels 2, 4, …), common
(`side: none` devices, panels after the last B panel). A and B streams are
filled in lock-step so panel 2n is the mirror of panel 2n − 1; the B panels are
written as `mirror_of` the A panel (today's mechanism, so tags swap A→B, 1→2).

**R7 Overrides.** `layout.overrides` move a device or pair after the automatic
fill; `layout.removed` drops it before the fill. A move that does not fit is a
check-report error, not a silent reflow. Overrides survive re-running the
layout; a device no longer present is reported and the override ignored.

**R8 Blank plates in the BOM.** Each panel's group A (enclosure) gains one row
`blank_plate_part` × (k − 1). Q25 asks Ali to confirm this is wanted.

**R9 Tags.** Unchanged rules; numbering follows the generated panel order
(`PSA1-L1-ESW-A11 to A1<n>` for n L1 switches in panel 1).

**R10 Golden.** Running the layout on the new example substation reproduces
`examples/panels/psa1..3.yaml` byte-for-byte except the `generated` header, so
every existing golden value holds.

## 5. Engine and pipeline change

New step **0 — layout**, before step 1 of "Data model and generation order":

```
substation.yaml + library ──sizing (R1–R3)──▶ NetworkPlan
                          ──layout (R5–R7)──▶ panels/*.yaml (generated)
panels/*.yaml ──existing steps 1–15──▶ workbook, check report
```

Modules: `engine/sizing.py` (R1–R3, pure functions), `engine/layout.py`
(R5–R7), `io/substation.py` (new models + loader), `cli.py` gains
`bomgen layout --substation <file>` and `bomgen build` runs layout first unless
`--no-layout`. Check report gains: port demand vs capacity per switch, panel
fill per panel, overrides that no longer apply, IED count.

## 6. What does not change

Tag naming, DC/AC distribution, terminal strips, grounding, HWIO, power and
heat calculations, sheet formats, writer, library packages (`.bomlib`), the
installer. Hand-written panels still work (`--no-layout`), which keeps the spec
example and every golden test valid during the transition.
